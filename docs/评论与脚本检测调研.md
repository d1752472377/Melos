# 歌曲评论与「服务端脚本检测页」调研

> 调研日期：2026-11-11
> 参考实现：`F:\dgn\音乐参考\Q-music`（LX Music 系，Apache-2.0）
> 脚本宿主：`E:\code\music\qmusic-script-host`
> 结论先说：**评论能只看不发，不需要任何账号，封装风险很低；脚本引擎能上服务器，但必须先解决沙箱逃逸。**

## 一、歌曲评论

### 1.1 Q-music 怎么做的

5 个平台各一个文件，共约 770 行，全部**只读**：

| 文件 | 行数 | 平台 |
|---|---|---|
| `src/renderer/utils/musicSdk/wy/comment.js` | 208 | 网易云 |
| `src/renderer/utils/musicSdk/tx/comment.js` | 282 | QQ 音乐 |
| `src/renderer/utils/musicSdk/kg/comment.js` | 101 | 酷狗 |
| `src/renderer/utils/musicSdk/kw/comment.js` | 82 | 酷我 |
| `src/renderer/utils/musicSdk/mg/comment.js` | 96 | 咪咕 |

每个文件导出 3~4 个方法，形状统一：

```
getComment(musicInfo, page, limit)   → { source, comments[], total, page, limit, maxPage }
getHotComment(musicInfo, page, limit) → 同上
getReplyComment(...)                  → 楼中楼（仅 kg/mg 有）
filterComment(rawList)                → 统一成 { id, text, time, timeStr, userName, avatar,
                                                   userId, likedCount, location, images, reply[] }
```

界面在 `PlayDetail/components/MusicComment/index.vue` + `CommentFloor.vue`：
「热门 / 最新」两个 tab、分页、楼中楼缩进、头像、点赞数、图片、IP 属地、emoji 表情替换。

### 1.2 关键结论：评论全程匿名，不碰账号

**在这一层没有任何 cookie、token、uin、登录态。** 我把 5 个 comment.js 全读了一遍，也 grep 了写操作：

- `grep -i "sendComment|postComment|发表|点赞|replyComment"` → **零命中**，Q-music 根本没有"发评论"功能
- 网易用 `weapi` 加密但**不带 MUSIC_U cookie**
- QQ 固定 `uin: '0'`
- 酷狗固定 `kugouid=0`、`clienttoken=` 为空
- 酷我固定 `uid=0`
- 咪咕不传任何身份

你说的「支持多个音乐账号登录实现的评论」——那条路在 Q-music 里其实**是给别的东西用的**：`MusicAccountProvider = 'tx' | 'wy' | 'kg'` 只出现在「每日推荐」和「从其他平台导入歌单」两处（`views/Search/components/BlankView.vue`、`views/List/MyList/components/ExternalImportModal.vue`）。评论一行都没用到。

**所以"只看不发"不是折中方案，就是 Q-music 本来的形态。** 也不存在"用别人账号发评论被封"的问题——我们根本不发。

### 1.3 我实测的接口（今天，2026-11-11）

四个平台全部拿到真实数据：

| 平台 | 端点 | 鉴权 | 实测 |
|---|---|---|---|
| 网易 | `GET https://music.163.com/api/v1/resource/comments/R_SO_4_<id>?limit=&offset=` | 无 | ✅ 200，total 1,969,885，首页带 15 条热评 |
| 酷狗 | `GET http://m.comment.service.kugou.com/r/v1/rank/newest?<params>&signature=<md5>` | md5 签名 | ✅ 200 |
| 酷我 | `GET http://ncomment.kuwo.cn/com.s?type=get_comment&sid=<rid>&start=&count=` | 无 | ✅ 200 |
| QQ | `POST http://c.y.qq.com/base/fcgi-bin/fcg_global_comment_h5.fcg`（需数字 songId） | 无 | ✅ 200，total 230,665 |
| 咪咕 | `GET https://app.c.nf.migu.cn/MIGUM3.0/user/comment/stack/v1.0?resourceId=<songId>` | 无 | 接口返回 000000（成功），但我手上的 resourceId 是占位值，未取到真实数据 |

几点实测细节：

- **网易有更简单的一条路**：`/api/v1/resource/comments/R_SO_4_<id>` 不需要 `weapi` 加密（Q-music 用的是加密那条）。上面这条 GET 直接可用，分页 `offset` 正常，首页附带的 `hotComments` 就是热评。
- QQ 的评论接口只认**数字 songId**，不认 songmid。用 `u.y.qq.com/cgi-bin/musicu.fcg` 的 `music.pf_song_detail_svr` 可以从 mid 换到数字 id，实测 **1.1 秒**。
- 频控暂未触发：网易连发 10 次全 200；酷我、酷狗各连发 6 次全 200。不过读评论本质上仍是爬取，**该做节流和缓存**。

### 1.4 和 Melos 现有歌曲 ID 的契合度（重要）

Melos 的 `Song.id` 各平台含义不同，逐一对照：

| Melos 平台 | `Song.id` 实际是 | 评论接口需要 | 能否直接用 |
|---|---|---|---|
| `netease` | 网易歌曲 id | `R_SO_4_<id>` 的 id | ✅ **直接用** |
| `kuwo` | `MUSICRID` 去掉 `MUSIC_` 前缀 | `sid=` | ✅ **直接用** |
| `kugou` | `FileHash` | `extdata=` / `schash=` | ✅ **直接用**（大小写都行） |
| `qq` | `mid`（songmid） | **数字 songId** | ⚠️ 需转换 |
| `migu` | — | `resourceId` | ❌ Melos 无咪咕内置搜索（`hasBuiltin = false`），App 里不会有咪咕歌曲 |

QQ 那个转换其实有个现成的捷径：Melos 自己的 QQ 搜索响应里**本来就有数字 `id`**（实测搜「晴天」返回 `id=97773 mid=0039MnYb0qxYhV`），只是 `searchSongsQq()` 目前只取了 `mid`。要么搜索时把 `id` 一起存下来，要么评论时现查一次（1.1 秒，可缓存）。

**所以 4 个有内置搜索的平台里，3 个拿现有 ID 就能直接拉评论，QQ 补一个字段即可。**

### 1.5 风险与建议

| 风险 | 评估 |
|---|---|
| 封号 | **无**。评论全程匿名，不带任何账号凭证，没有可封的东西 |
| 接口风控 / IP 限流 | 有，但实测频次下未触发。需要节流 + 缓存 |
| 接口失效 | 有。这几条都是非公开接口，平台随时可能改。要做好"取不到就静默降级" |
| 法律/合规 | 只读公开内容，不存储不外传，风险低于直接取音频流本身 |

建议形态：

1. **只做「热门 + 最新」两栏 + 分页 + 楼中楼**，不做点赞、不做回复、不做发布。
2. 走 Melos **自己的后端中转**（`/api/comment?platform=&id=&page=`），好处有三个：客户端不用带 5 套签名逻辑；服务端统一节流与缓存（同首歌同一页 5 分钟内复用）；UA / 出口 IP 统一，不易被单个用户的行为带崩。
3. 入口放播放页——`PlayerScreen` 已经有 `PlayerControlCenterSheet` / `SongAudioDetailSheet` 两个抽屉，加第三个「评论」抽屉即可，交互与现有底栏一致。
4. 补 QQ 数字 id：`PlatformMusicService.searchSongsQq()` 里把 `id` 一起读出来。

## 二、把脚本引擎放到服务器

### 2.1 现状

`qmusic-script-host` 已经是「一份 JS 两端跑」：

- `build/lx-core.js`（304 KB）—— 纯 JS，无平台依赖，APK 的 QuickJS 和服务器 Node 跑**同一份**。
- 实测 Melos 的 `assets/script/lx-core.js` 与 `build/lx-core.js` **逐字节相同**（只差 CRLF/LF），说明两边确实同源。
- 运行时只依赖 `node:` 内置模块，**零 npm 运行时依赖**；整个目录去掉 `node_modules` 后 **1.6 MB**。
- 已经自带一个网页版（`web/server.js`，默认 `127.0.0.1:8099`），提供 `/api/run`、`/api/probe`、`/api/probes`、`/api/check`、`/api/search` —— 其实就是你要的那个"脚本运行检测页"的原型。

### 2.2 服务器可行性实测（100.64.0.9，Node v20.20.2）

我把整个仓库传到服务器 `/tmp/qsh` 跑了一遍：

```
node cli.js run examples/demo-source.js      → init OK  828 ms
node cli.js run <真实用户脚本 44KB>            → init OK 1095 ms
单次运行内存                                  → RSS +10.9 MB（峰值约 62 MB）
node cli.js probe ... --source kw --song-id 228908 → 脚本自己的后端返回"当前版本已停止服务"
```

最后那条其实是**很有价值的信号**：这是从服务器数据库 `user_scripts` 表里取的真实用户脚本（"长青SVIP音源 v1.2.0"），脚本自身后端已经下线了。也就是说**服务端检测页确实能提前发现"用户装了个死脚本"**，这正是它的意义。

服务器资源：2 核 / 1.87 GB 内存（当前可用约 1.15 GB）/ 30 GB 空闲磁盘。单次 ~60 MB，够用，但要限并发。

### 2.3 ⚠️ 必须先解决：沙箱能逃逸（实测确认）

这是整个方案的**前置阻塞项**。`src/node/runtime.js` 用的是 Node 的 `vm.createContext()`，而 **Node 官方明确说 vm 不是安全边界**。我写了几个探测脚本，通过 `cli.js run` 实际跑：

```js
const F = (0, eval)('this').constructor.constructor
F('return process.version')()      // → "v24.9.0"  ← 拿到宿主 process
F('return Object.keys(process.env).length')()   // → 144     ← 读到全部环境变量
process.binding('spawn_sync').spawn({ file: '/bin/sh', ... })  // ← 真的起了进程
```

在服务器上同样成立（Node 20.20.2）：

```
-- bare:        ESC env=19 spawn=reachable
-- permission:  ESC env=19 spawn=blocked
```

含义很直白：**任何一个用户上传的音源脚本，都能在服务器上以运行者的身份执行任意命令、读取全部环境变量。** 而 Melos 后端 `/opt/melos-backend/.env` 里有 `RELEASE_TOKEN` 和 `GITHUB_TOKEN`。按现在的样子把这个页面上线 = 把 RCE 和发行密钥一起挂在公网上。

另外 `--experimental-permission` 只挡住了 `process.binding`（spawn 被禁），**挡不住读 `process.env`**；而且它在 Node 20 上还是实验特性。

第二个坑：**死循环脚本会永久卡住宿主进程**。`while(true){}` 实测让 `cli.js run` 一直挂着，`initTimeout` 管不到（它是事件循环上的定时器，被同步死循环饿死）。只能靠外部 SIGKILL。

顺带确认：**子进程 + SIGKILL 这个组合是有效的** —— 我在父进程里 spawn 一个跑死循环脚本的子进程，6 秒后 SIGKILL，父进程完全不受影响，还能继续服务。

### 2.4 建议的部署形态

不要把这个页面塞进 Go 后端进程里，也不要裸跑 `web/server.js` 对外。推荐：

```
nginx (公网 443)
   └── /admin/api/script-check/*   →  127.0.0.1:8790  (Node 检测服务，独立进程)
                                        └── 每次都 spawn 一个子进程跑脚本
                                             node --permission --allow-fs-read=<沙箱目录>
                                             + 清空 env + 非 root 用户
                                             + 15s 硬超时 SIGKILL
                                             + 并发上限 2
```

必须同时做到：

1. **独立进程、独立用户**：用 `nobody`（服务器上存在，uid 65534）跑，绝不 root。pm2 里 `pm2 start ... --uid nobody`。
2. **清空环境变量**：子进程 spawn 时 `env: {}`，只放最小集合（`PATH`、`HOME`、`TMPDIR`）。上面实测过 `process.env` 能全读，这一步不能省。
3. **`--experimental-permission --allow-fs-read=<唯一脚本目录>`**：挡掉 `process.binding` 和无关文件读取。它挡不住读 env，所以第 2 条必须做。
4. **每次运行都起子进程 + 硬超时 SIGKILL**：不要在同一进程里 `vm` 里跑第二次。实测这是唯一能兜住死循环的办法。
5. **并发上限 + 队列**：单次 60 MB / 1 秒，2 核机器上并发 2 就是上限。
6. **脚本来源只从数据库读**，不要接受任意路径（现有 `web/server.js` 的 `resolveScriptPath` 已经有目录白名单，保留）。
7. **管理端鉴权**：检测服务的接口要走现有 admin Bearer token 校验（`backend-go` 的 `requireAdmin`），或者单独一个 token。

### 2.5 页面上该有什么

现有 `web/index.html` 基本够了（选脚本 / 选 runtime / 跑 init / 按平台探测 / 检查更新 / 搜索真实 ID）。搬到服务端后建议：

- 脚本列表直接读 `user_scripts` 表（现在有 4 条 / 3 个用户），不用扫文件目录
- 每个脚本一行：名称、作者、版本、声明了哪些源/音质、**上次检测结果**
- 一键「全部检测」：对每个脚本跑 init + 每个声明平台探一次 `musicUrl`，把结果写回库（`last_check_at` / `last_check_status`）
- 检测结果和现有「客户端日志」页同风格：绿=正常、黄=偏慢、红=失败（脚本自报的错误原样带上）

## 三、两件事的依赖关系

两件事**互不依赖**，可以分开做：

- **评论**只动客户端（加抽屉）+ 后端（加中转接口），不碰脚本引擎。
- **脚本检测页**只动服务器和 admin，不碰客户端。

如果排优先级：评论是给用户的功能，检测页是给你自己的运维工具。评论的实现风险更低（只读、匿名、接口已实测可用），建议先做。
