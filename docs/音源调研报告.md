# 音乐 App「音源」调研报告

> 面向：原生 Android 播放器 + 后端音源管理。本文聚焦"音源"是什么、怎么用、有哪些可用方案、法律风险、以及后端管理该怎么做。
> 调研时间：2026 年（以 GitHub 项目当前状态为准）

---

## 一、先说结论：什么是「音源」

在你这个 App 的语境里，「音源」不是音频文件，而是**一套能把"歌曲"变成"可播放地址 + 元数据 + 歌词"的数据源/接口**。

一个音乐 App 的播放器本身什么歌都没有。它要做的事是：

1. 拿到一个"歌单/搜索词"；
2. 向某个"音源"查询，得到歌曲列表（歌名、歌手、专辑、封面、歌曲唯一 ID）；
3. 向音源请求这首歌的**真实可播放 URL**（mp3/m4a/flac 直链，可能带防盗链 header）；
4. 向音源请求**歌词**；
5. 播放器负责把 URL 交给系统播放器/ExoPlayer 播放。

所以「音源」的核心能力 = **搜索 + 取播放直链 + 取歌词 + 取歌单/专辑/榜单**。你说的"后端管理音源的添加/切换"，本质就是：**后端维护一个音源插件库，App 通过后端统一接口去调不同的音源，后端可以随时加新音源、下线坏音源、按策略切换/降级。**

## 二、音源的标准接口长什么样（最重要的一节）

音源各家实现不同，但社区已经收敛出一套事实标准。最完整的参考是 **MusicFree 的插件协议**（下面就是它的接口）。你后端做"音源抽象"时，直接照这个协议设计即可。

### 2.1 插件属性（描述音源的元信息）

| 字段 | 含义 |
|---|---|
| `platform` | 音源名（唯一标识，如 "netease"） |
| `version` | 版本号（semver，用于更新判断） |
| `author` | 作者 |
| `srcUrl` | 插件远程更新地址（指向 .js 文件） |
| `cacheControl` | 缓存策略：`cache` / `no-cache` / `no-store`（音源 URL 有过期时间的要用 no-cache/no-store） |
| `primaryKey` | 主键字段，默认 `["id"]`，某些源需要多个字段定位资源 |
| `supportedSearchType` | 支持的搜索类型：`music/album/artist/sheet/lyric` |

### 2.2 插件函数（音源要实现的能力）

| 函数 | 入参 → 出参 | 作用 |
|---|---|---|
| `search(query, page, type)` | → `{isEnd, data: IMusicItem[]}` | 搜索歌曲/专辑/作者/歌单/歌词 |
| **`getMediaSource(musicItem, quality)`** | → `{url, headers?, userAgent?}` | **取真实播放直链（最核心）**，quality ∈ low/standard/high/super |
| `getMusicInfo(musicItem)` | → `Partial<IMusicItem>` | 补全歌曲详情（封面等） |
| `getLyric(musicItem)` | → `{rawLrc, translation?}` | 取歌词（含翻译） |
| `getAlbumInfo(albumItem, page)` | → `{isEnd, musicList, albumItem}` | 专辑详情 + 歌曲列表 |
| `getMusicSheetInfo(sheetItem, page)` | → `{isEnd, musicList, sheetItem}` | 歌单详情 + 歌曲列表 |
| `getArtistWorks(artistItem, page, type)` | → `{isEnd, data}` | 作者作品 |
| `importMusicItem(urlLike)` | → `IMusicItem` | 从 URL/ID 导入单曲 |
| `importMusicSheet(urlLike)` | → `IMusicItem[]` | 从 URL/ID 导入歌单 |
| `getTopLists()` | → `IMusicSheetGroupItem[]` | 榜单列表 |
| `getTopListDetail(topListItem, page)` | → `{isEnd, musicList}` | 榜单详情 |
| `getRecommendSheetTags()` | → 推荐歌单 tag | 推荐分类 |
| `getRecommendSheetsByTag(tag, page)` | → 歌单列表 | 按 tag 取歌单 |

### 2.3 关键设计点（你后端照抄这套）

- **歌曲模型统一**：`IMusicItem` 至少包含 `id`（源内唯一）、`platform`（哪个源）、`title`、`artist`、`album`、`artwork`、`url`（可选）。跨源搜索时用 `platform` 区分来源。
- **取直链是异步的、可能失败**：`getMediaSource` 可能拿不到（VIP/下架/防盗链失效），所以 App 和音源都要有**降级**：换音质 → 换音源 → 失败跳过。
- **防盗链**：很多源返回的直链必须带特定 `headers`（Referer/User-Agent/Cookie），否则 403。接口里 `headers` 字段就是干这个的。
- **直链会过期**：所以 `cacheControl` 要设对，播放时尽量现取。

## 三、主流音源/聚合方案盘点（含现状）

### 3.1 NeteaseCloudMusicApi（网易云 Node API）—— 已删库 ⚠️

- 原仓库 Binaryify/NeteaseCloudMusicApi，30k+ star，**2024 年 1 月被作者清空**，README 只剩"保护版权，此仓库不再维护"。
- 参考新闻：[IT之家《出于"保护版权"，网易云音乐第三方开源 API GitHub 删库停更》](https://www.ithome.com/0/746/942.htm)
- 现状：GitHub 上有大量 fork（如 gmg137/netease-cloud-music-api 等），但很零散、质量参差、随时可能被下架。
- 意义：这是"逆向聚合 API"路线的代表，证明这条路**法律风险高、不可持续**。

### 3.2 meting —— 仍在维护的聚合库 ✅

- 地址：<https://github.com/metowolf/Meting>（PHP 原版）+ Node 版 `@meting/core`。
- 统一接口覆盖：**网易云 / QQ(腾讯) / 酷狗 / 百度 / 酷我**。
- 提供 `search / song / album / artist / playlist / url(取直链) / lyric / pic`，`format(true)` 后各平台返回统一 JSON 结构。
- 另有 RESTful 封装 [injahow/meting-api](https://github.com/injahow/meting-api)，**这最接近你说的"后端音源管理"**——一个 HTTP 服务聚合多源。

### 3.3 洛雪音乐（lx-music）—— 自定义源机制

- 桌面版 lx-music-desktop / 移动版 lx-music-mobile，Electron + Vue。
- 播放器本身不拿音频，靠"自定义源"返回在线链接（协议里写得很清楚）。
- 内置源历史上有酷我/酷狗/咪咕等；社区自定义源是独立 JS 脚本，实现一套约定接口。
- 协议很谨慎：明确声明数据来自公开服务器、非商用、仅学习研究。

### 3.4 MusicFree 插件生态 —— 协议最规范 ✅

- 播放器：<https://github.com/maotoumao/MusicFree>（Android/HarmonyOS/桌面版）。
- 插件协议：<https://musicfree.catcat.work/plugin/protocol.html>（第二节就是从这里总结的）。
- 插件本质：一个 **CommonJS 模块**，`module.exports` 导出属性和函数。
- ⚠️ 重要现状：示例插件仓库 <https://github.com/maotoumao/MusicFreePlugins> **已因收到版权"告知函"移除所有国内厂商音源**（网易云/QQ/酷狗/酷我/咪咕）。
- 当前示例插件只剩：`youtube / audiomack / bilibili / webdav / navidrome / airsonic / kuaishou / maoerfm / suno / udio / yinyuetai / 歌词千寻 / 歌词网`。

> 小结：**国内主流音乐厂商（网易云/QQ/酷狗/酷我/咪咕）的逆向音源，这几年被版权方系统性打击，开源仓库一个接一个下架。** 这是你立项前必须正视的现实。

## 四、各音源厂商的"拿到直链"技术原理（逆向路线，不稳定、有风险）

> 以下均为"从公开网页/App 接口逆向"的原理，供理解"音源内部怎么干活"用，**不要作为商业产品依赖**。

| 厂商 | 关键标识 | 搜索入口（示意） | 取直链要点 |
|---|---|---|---|
| 网易云 | 歌曲 `id` | `music.163.com/api/cloudsearch/pc` | `/weapi/song/enhance/player/url/v1`（需 `params`+`encSecKey` 加密），或公开跳转 `music.163.com/song/media/outer/url?id={id}.mp3`；需 Referer/Cookie |
| QQ音乐 | `mid` | `u.y.qq.com/cgi-bin/musicu.fcg`（JSON + 签名） | 返回 `purl`（vkey 鉴权相对路径），需拼 CDN 域名 / `getCdnDispatch` |
| 酷狗 | `hash` | `mobilecdn.kugou.com/api/v3/search/song` | `wwwapi.kugou.com/yy/index.php?r=play/getdata&hash=...` 返回 `play_url` |
| 酷我 | `rid` | `kuwo.cn/api/www/search/searchMusicBykeyWord`（需 csrf/kw_token Cookie） | `kuwo.cn/api/v1/www/music/playUrl?mid={rid}` |
| 咪咕 | `copyrightId` | `m.music.migu.cn/migu/remoting/scr_search_tag` | `c.musicapp.migu.cn/MIGUM2.0/v1.0/.../listenSong.do?copyrightId=...` |

共同点：**都要模拟浏览器请求头、处理签名/加密、处理防盗链、处理直链过期**，且官方随时改接口导致失效。

## 五、法律 / 版权风险（立项前必看）

1. **逆向公开接口拿歌**：处于灰色地带。未登录抓公开数据，厂商未明示禁止时"学习研究"尚可；但**用于商业 App 向公众提供播放**，几乎必然侵权（信息网络传播权），已被大量维权（网易云删库、MusicFree 收到告知函都是实证）。
2. **抓取 VIP/付费/试听歌曲**：直接违法，务必过滤掉 VIP/付费/试听（MusicFree 示例插件也明确过滤）。
3. **个人学习 vs 商业产品**：差异巨大。你要做的是一个"音乐 App"，如果面向公众、有商业属性，逆向音源不可行。

**合法可走的路线：**

| 路线 | 说明 | 门槛 |
|---|---|---|
| 官方开放平台 | 腾讯音乐开放平台、网易云/酷狗开放平台等 | 多需企业资质/审核，个人难拿完整播放权限 |
| 版权采购 | 向版权方/数字音乐版权服务商采购曲库 | 贵，需资质 |
| 自建曲库 | 用户上传 + 自有版权内容 + 公版内容 | 曲库来源是难点 |
| 合法 API | Spotify / Apple Music / YouTube Data / SoundCloud 等海外官方 API | 有配额/地域/授权限制 |
| 自托管音源 | webdav / navidrome / Jellyfin 等，放自己服务器上的歌 | 内容需合法 |

## 六、对你「后端管理音源」的架构建议

### 6.1 总体架构

```
Android App (ExoPlayer)
        │  统一业务 API（search / songUrl / lyric / playlists ...）
        ▼
后端音源网关（你的核心模块）
        │  按"音源路由策略"分发
        ▼
   ┌──────────┬──────────┬──────────┬──────────┐
   │ 音源A     │ 音源B     │ 音源C     │ 自建曲库  │
   │ (网易云)  │ (QQ)     │ (酷我)    │ (webdav/OSS)│
   └──────────┴──────────┴──────────┴──────────┘
```

### 6.2 后端要做的事（对应你说的"添加/切换"）

1. **音源抽象层（接口）**：后端内定义一个统一的 `MusicSource` 接口（照 2.2 的协议），每个音源是一个实现。
2. **音源注册表 + 配置**：数据库存音源列表（id、名称、类型、启用状态、权重、cookie/密钥、优先级）。管理后台可增删改。
3. **路由/切换策略**：
   - 用户搜索 → 聚合多个启用音源的结果（按 platform 去重/合并）；
   - 取直链失败 → 自动降级（同源换音质 → 换下一个音源 → 返回失败）；
   - 音源整体健康度监控（失败率、延迟），坏了自动下线或降权。
4. **灰度/热切换**：改音源配置**无需发版**，App 永远只调后端，后端决定背后用哪个源。
5. **缓存与风控**：直链短期缓存、按音源做限流、统一出口 IP/UA。

### 6.3 建议的技术选型（供参考）

- 后端：Node.js（可直接复用 meting / @meting/core 或 NeteaseCloudMusicApi fork 的逻辑）或 Go/Java。
- 最省事起步：**基于 `@meting/core` 或 `injahow/meting-api` 包一层自己的管理后台**，先把"音源增删/切换/降级"的架子搭起来。
- App 侧：只对接你自己的后端统一 API，不认识任何具体音源。

## 七、实测验证（2026-08，meting `@meting/core` 实跑结果）

在本机 `research/meting-demo` 下用 `@meting/core` 实际调用，结果如下（关键字「晴天」）：

| 音源 | 搜索 | 取直链 | 歌词 | 备注 |
|---|---|---|---|---|
| netease 网易云 | ✅ | ✅ **HTTP 200，audio/mpeg，11MB mp3** | ✅ | 最稳，全链路可用 |
| tencent QQ音乐 | ✅ | ❌ 返回空 URL | — | 搜索正常，取直链失效（免费歌也要 vkey/cookie） |
| kugou 酷狗 | ✅ | ❌ 返回空 | — | 同上 |
| kuwo 酷我 | ❌ 返回 undefined | ❌ | — | 搜索接口已改（需 csrf/kw_token） |
| baidu 百度 | ❌ 返回 undefined | ❌ | — | 基本失效 |

### 关键发现

1. **只有网易云源是"全通"的**，其它源在 meting 里的取直链/搜索逻辑已经过时失效。
2. **网易云公开接口拿不到 VIP/版权歌曲**：搜「晴天」返回的是翻唱版（Lucky小爱、RyaVocal 等），不是周杰伦原版——原版在网易云受版权/VIP 限制，公开接口只能拿到可免费播放的版本。
3. 这正好证明了架构判断：**音源会随时失效，后端必须做多音源注册 + 降级 + 健康度监控**，不能把某个源写死在 App 里。
4. 起步建议：**主用 netease 源**（meting 直接可用），其它源作为"注册表里的占位"，后续谁家接口通了就启用谁。

## 八、下一步可以做的事

1. **定位已确认**：学习产品、无用户、不盈利、不公开——按逆向音源路线推进即可。
2. **选定首个音源**：netease（meting 已验证全链路可用）。
3. **搭后端骨架**：定义 `MusicSource` 接口 + 音源注册表 + 管理接口（增删改查 + 启用/禁用 + 权重 + 降级）。
4. **再回到 Android**：ExoPlayer 播放 + 调后端 API 的播放器 MVP。

## 九、用户自备音源：妖狐酷我 API（已实测可用 ✅）

用户提供的第三方聚合 API，封装成标准音源后全链路可用。

### 基本信息

- 接口：`https://api.yaohud.cn/api/music/kuwo`（GET，返回 JSON）
- API Key：`zNPP9p4P7d4Bku9wZAp` ｜ Secret Key：`ae640d49842571c76dd3cb69b4f45450`
- 签名：`HMAC-SHA256("key={apiKey}&timestamp={秒级时间戳}", secretKey)` → hex
- 请求头：`X-Api-Key` / `X-Api-Timestamp` / `X-Api-Sign`（注意 `key` 还要放在 URL query）
- 限制：**QPS 每 2 秒 5 次**；播放链接有时效性，过期需重新请求

### 实测结论（Node 封装在 `research/yaohud-kuwo/kuwo-source.mjs`）

| 能力 | 结果 |
|---|---|
| 搜索 `msg=周杰伦` | ✅ 返回原版歌曲（晴天/叶惠美、红尘客栈/十二新作…），带 `image` 封面 |
| 取单曲 `action=song&id=rid` | ✅ 返回直链 + 歌词 + 时长 |
| 直链可达性 | ✅ HTTP 200，`audio/x-flac`，55MB 无损 |
| 歌词 | ✅ `lyric.lrc` 文本 + `lyric.lrclist` 逐行时间戳 |

### 踩坑记录（重要，后端接入必看）

1. **`msg` 参数始终必填**——即使 `action=song` 也要传（接口实现与文档示例不符，文档写 `action=song&id=xxx` 即可，实际报"参数 msg 为必填"）。封装里用歌曲 title 填 msg。
2. **两种取单曲模式字段名不同**：
   - `action=song&id=rid` → 歌手字段是 `artist`（另有 `duration`/`rid`）
   - `msg&n=序号` → 歌手字段是 `songname`
   - 封装统一取 `artist || songname`。
3. **`action=song` 模式忽略 `size` 音质参数**，无论请求 Standard/SQ/hires，都返回无损 flac（bitrate 2000）。要指定音质需用 `msg&n` 模式（`SQ` 能拿到 320k mp3）。
4. **会间歇性返回 503**（nginx，上游酷我/代理过载）——必须在封装层做**自动重试 + 指数退避**（已实现）。

### 与 meting 的关系

meting 里的酷我源已失效，而**这个 API 是可用替代**，且比 meting 的网易云源更全（无损 + 歌词一次返回 + 原版歌曲）。后端起步建议：**把这个作为主音源，netease(meting) 作为备选降级音源。**
