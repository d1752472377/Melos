P1 重要 — 影响可维护性与安全性

P1-1MainViewModel 是 1,612 行的"上帝对象"

单文件承载 85 个函数、约 90 个 StateFlow，职责横跨：搜索、历史、收藏、歌单增删改、FM 电台漂移算法、云同步（含互斥锁与待删重放）、音源脚本导入、歌手/专辑/榜单详情、缓存统计、用户资料。

其中 FM 漂移、云同步 LWW、脚本生命周期三块各自的内部状态（fmDriftArtists、fmQueuedIds、pendingDeletedCloudIds、4 个请求令牌、syncMutex）耦合在同一个类里，任何一个改动都需要通读全文才能确认影响面。

建议 按功能域拆分为 SearchViewModel / PlaylistViewModel / FmViewModel / SyncViewModel / ProfileViewModel，保留一个薄的 AppShellViewModel 只管理导航与全局 Toast。可先拆最独立的 FM 与同步两块，风险最低。
P1-2AppShell 单个 Composable 长达 942 行

ui/AppShell.kt 共 1,074 行，其中 fun AppShell(...) 一个函数从第 90 行一路写到第 1034 行——整个文件的 @Composable 只有 2 个。文件里的页面切换、抽屉、各类 Sheet、Snackbar、缓存刷新协程全部内联在这一个函数体内。

这种结构会带来实际代价：Compose 无法对超大函数做细粒度重组跳过；任何一处状态变化都可能触发大范围重算；且 IDE 的 Compose 预览基本失效。

同类问题还有 SettingsScreen（564 行）、PlaylistDetailScreen（549 行）、ProfileScreen（423 行）、PlayerScreen（380 行）。

建议 按"一个 Overlay/Sheet 一个 Composable"抽取，把 AppShell 降到 150 行以内的纯路由与装配层。参考同项目 ui/components/ 已经做得很好的拆分方式。
已修复登录 token 明文存放于 SharedPreferences

UserStore 与 SyncServerStore 把认证 token 直接 putString 进普通 MODE_PRIVATE 的 SharedPreferences，没有加密。项目已用 backup_rules 把登录态排除出云备份，但明文落盘仍意味着 root 设备与 adb backup 可直接取走 token，进而访问用户的私有云同步数据。

⚠ 本条目初版给出的方案是错的，此处更正：初版建议使用 androidx.security:security-crypto 的 EncryptedSharedPreferences。该库已于 1.1.0-alpha07（2025-04）废弃全部 API，1.1.0-beta01（2025-06）重申，且稳定版 1.1.0 只是把废弃 API 原样带出来。官方说明仅一句："Deprecated all APIs in favour of existing platform APIs and direct use of Android Keystore"——未提供迁移指南。

已采用方案 新增 TokenCipher，直接使用 AndroidKeyStore 生成不可导出的 AES-256-GCM 密钥加解密 token，不引入已废弃依赖。要点：
· 存储值带显式版本前缀（v1:<base64(iv‖ciphertext)>），而非"解密失败就当明文"——避免损坏的密文被当作有效 token 发出去
· 兼容历史明文：读到无前缀的值原样放行，并顺带就地升级为密文，老用户不掉登录
· 解密结果带内存缓存——OkHttp 拦截器每个请求都会读 token，不走缓存则每次请求都要过一次 Keystore
· 密钥不随云备份迁移，与"登录态排除出备份"策略一致：换机解不开即要求重新登录
已修复APK 升级包仅用 MD5 校验

UpdateService 从固定域名 music.dovislab.com/update.json 拉取升级信息，下载后校验大小与 MD5。MD5 已不具备抗碰撞能力。

⚠ 本条目初版把风险说重了，此处更正：初版称这构成"完整的远程代码执行路径"。实际复核代码后发现，UpdateService 在摘要校验之后还有一道 verifyApkSignature()，比对下载包的签名证书与当前已安装应用是否一致——伪造包会在这一步被拦下。代码里的注释其实已经点明了这个层次："md5/url 都出自同一 TLS 通道，属于自证，签名校验才是独立信任锚点"。因此 MD5 的弱点属于纵深防御层面的问题，而非可直接利用的漏洞。

已采用方案 新增 sha256 字段并优先采用，保留 md5 回退以兼容历史 update.json 与仍在读旧格式的已装版本。算法选择与流式摘要提取为纯函数 selectDigestSpec / computeFileDigest 并加了单元测试（含 64KB 缓冲区边界用例）。CI 侧 update.json 现在同时下发两个字段。
P1-556 个 public 可变状态直接暴露给 UI

项目中存在两种互相矛盾的写法：41 处遵循了正确范式（private val _x = MutableStateFlow(...) + val x = _x.asStateFlow()），但有 56 处直接暴露了 MutableStateFlow，例如：

  • MainViewModel.kt:69 — val currentTab = MutableStateFlow(AppTab.HOME)
  • MainViewModel.kt:70-81 — showPlayer、showSettings、showLogin 等 12 个弹层开关
  • MainViewModel.kt:121-134 — isLoadingContent、contentError、sheetCat 等

后果是 UI 层可以绕过 ViewModel 的方法直接 viewModel.showPlayer.value = true，状态变更散落各处、不可追溯，也让 ViewModel 无法保证不变量。

建议 统一收敛为 private val _x + asStateFlow()，仅对确实需要外部写入的场景提供具名方法（如 openPlayer()）。属于机械性重构，但建议配合编译期检查一次性做完，避免两种风格长期共存。

P2 改进项 — 技术债与规范性

已修复16 处静默吞异常

全项目 120 个 try 块中有 16 处 catch (_: Exception) {} 完全空实现，另有 27 处宽泛的 catch (Exception)。多数出现在持久化写入（SettingsStore、UserStore）与缓存清理中，从"不影响主流程"的角度可以理解，但一旦用户反馈"设置不生效/收藏丢失"，将没有任何线索可查。

建议 保留静默降级策略，但在 catch 内至少加一行 Log.w(TAG, "…failed", e)。对确实预期的失败可改为显式捕获具体异常类型。
P2-2国际化形同虚设：816 处硬编码中文 vs 1 条 string 资源

strings.xml 只有 app_name 一条，全项目 stringResource() 调用数为 0，而代码与布局中硬编码的中文字面量约 816 处。

如果产品定位就是纯中文单语言应用，这不算缺陷；但它同时意味着未来任何多语言需求都要重写全部 UI 文案层，且 Lint 的 HardcodedText 检查永远无法生效。

建议 至少把面向用户的关键路径（登录、设置、错误提示）先迁到资源文件；或明确在 README 声明"仅支持中文"，避免后续误解。

P2-5Locale 相关的隐性 bug（3 处）

AudioCacheService.formatSize() 三处使用 String.format("%.1f KB", …) 而未指定 Locale。在阿拉伯语、印地语等使用非拉丁数字或不同小数分隔符的系统语言下，会输出 1,5 MB 或阿拉伯数字，缓存页面显示将异常。

建议 统一改为 String.format(Locale.US, …)。文件大小属于机器可读格式，本就不该跟随系统语言。
P2-6compileSdk 37 触发 AGP 兼容告警

构建时输出："We recommend using a newer Android Gradle plugin to use compile SDK version 37.0"。当前 AGP 9.1.0 并未正式支持 compileSdk 37，属于"能编过但不被保证"的状态。同时 targetSdk = 35 落后于最新版本（Lint OldTargetApi）。

建议 升级 AGP 至 9.4.0 消除告警；targetSdk 待功能稳定后再评估提升（提升 targetSdk 会带来前台服务类型、通知权限等行为变更，需单独回归）。
P2-7死代码与无障碍问题

UpdateService.kt:79 的 @RequiresApi(FROYO) 与 :210 的 if (SDK_INT >= N) 在 minSdk = 24 下恒真，属于可删除的死代码（Lint ObsoleteSdkInt）。

悬浮胶囊的 float_capsule.xml 存在三处无障碍缺陷：字号 10sp 低于建议下限（SmallSp）、封面 ImageView 缺 contentDescription、自定义 onTouch 未在识别到点击时回调 performClick()（ClickableViewAccessibility，影响 TalkBack 可用性）。另有 3 处布局硬编码文案。

建议 清理死代码；字号提到 11sp 以上，为封面补 contentDescription，在 ACTION_UP 的轻点分支补 v.performClick()。
P2-8无 LICENSE 文件，且 lyrics 为未标注来源的第三方代码

整个仓库找不到任何 LICENSE 文件。lyrics 模块（4,799 行 / 40 文件）使用 com.mocharealm.accompanist.lyrics 包名，是被内联进仓库的开源第三方库，但模块内既无 README、也无版权头或 LICENSE 声明。

若该上游项目采用 GPL 等传染性许可证，当前的分发方式可能产生合规义务；即便为宽松许可证，缺少署名也不符合常见要求。

建议 确认上游许可证，在 lyrics/ 下放置对应的 LICENSE 与出处说明，并在仓库根补充项目自身的 LICENSE。
P2-9网络层设计上的两处隐晦点

其一，ApiClient 的 Retrofit baseUrl 是一个占位地址 127.0.0.1:8787，真实目标由拦截器在运行时重写 scheme/host/port。这个做法解决了"服务器地址可配置"，但让 baseUrl 具有误导性，也使网络层难以做单元测试（需要构造拦截器上下文）。

其二，PlatformMusicService 内联了约 15 条 https://music.163.com/api/... 字符串字面量散落在各方法中，接口一旦变更需全文搜索。

建议 把平台接口路径提取为集中的常量对象（或 @GET 注解形式），并考虑用 HttpUrl 参数化 baseUrl 以便测试。
P2-10StaticFieldLeak（经核实为误报，但建议加固）

Lint 报 FloatCapsuleManager 作为 object 持有 capsuleView: View 存在内存泄漏。经追踪调用链：唯一的 show() 调用点（PlayerManager.kt:211）传入的是 appContext，因此 View 持有的是 Application Context，不会泄漏 Activity；且 hide() 会把 capsuleView 置空。

不过作为 public 的全局单例，它无法阻止未来调用方误传 Activity Context——AppShell.kt:859 附近已在用 Activity 的 LocalContext 调用该类的其他方法，边界相当接近。

建议 在 show() 入口做一次 context.applicationContext 归一化，把这个约束从"约定"变成"代码保证"。
